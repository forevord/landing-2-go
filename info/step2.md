# Step 2 — Архитектура маршрутов и i18n

**Фаза:** Setup
**Зависит от:** Step 1
**Блокирует:** Step 3, Step 4 (любой текст должен сразу идти через i18n)

---

## Цель

Рабочая маршрутизация `/pl/` и `/en/`, зарезервированные слоты под будущие языки, и обязательное правило: ни одной строки текста в компонентах, минуя систему локализации — даже временных плейсхолдеров.

## Контекст из SPEC.md

Раздел 9 (Tech Notes), требование 1: маршрутизация с i18n с первого дня, даже если реально используется только `/pl/`. Зарезервировать `/de/`, `/cs/`, `/sk/` — без реализации контента. Раздел 6 (SEO): `hreflang` между `/pl/` и `/en/` — техническая база закладывается здесь, разметка добавится в Step 6.

## Что делать

1. **Выбор i18n-механизма**
   - Next.js App Router: локали через `[locale]` сегмент в структуре `app/[locale]/...`.
   - Библиотека для словарей: `next-intl` или встроенный механизм Next.js — зафиксировать один вариант и не менять посреди проекта.

2. **Список локалей**
   - Активные на MVP: `pl` (default), `en`.
   - Зарезервированные (в конфиге, без страниц и словарей): `de`, `cs`, `sk`.
   - Конфиг локалей должен быть в одном месте (`i18n.config.ts` или аналог), чтобы добавление нового языка в будущем было правкой одного файла, а не поиском по всему проекту.

3. **Структура словарей**
   ```
   /messages
     pl.json
     en.json
   ```
   - Ключи организованы по блокам страницы (совпадают с блоками из SPEC §4): `topbar`, `hero`, `services`, `whyUs`, `process`, `gallery`, `testimonials`, `faq`, `form`, `contacts`, `footer`.
   - Даже если контент EN на старте минимален/заглушка — ключи должны существовать в `en.json`, не должно быть fallback на PL по умолчанию (иначе переключатель будет выглядеть сломанным).

4. **Default locale и редиректы**
   - `/` редиректит на `/pl/` (или отдаёт `/pl/` без редиректа, если механизм это позволяет — предпочтительнее для SEO, меньше редиректов в цепочке).
   - 404 для несуществующих локалей (`/de/` пока не должен открываться как рабочая страница, раз контента нет).

5. **Переключатель языка (техническая часть)**
   - Компонент переключателя появится в Top Bar (Step 4), но логика маппинга «текущий путь → эквивалентный путь на другом языке» реализуется здесь, как переиспользуемая утилита.
   - Требование из SPEC §4: смена языка не должна сбрасывать на главную — переключатель должен сохранять текущий путь, только меняя локаль-сегмент.

## Критерий готовности

- [ ] `/pl/` и `/en/` открываются как отдельные роуты на пустой тестовой странице.
- [ ] Переход между `/pl/some-path` и `/en/some-path` сохраняет путь, меняя только локаль.
- [ ] `/de/`, `/cs/`, `/sk/` присутствуют в конфиге локалей, но не дают рабочих страниц (это ожидаемо на MVP).
- [ ] В коде нет ни одной строки видимого пользователю текста вне `messages/*.json` — проверить контрольным поиском по репозиторию.
- [ ] Тестовая страница на `/en/` отображает текст из `en.json`, а не fallback на польский.

## Почему до вёрстки компонентов

Перенос захардкоженных текстов в i18n постфактум — самый частый источник техдолга на подобных проектах: каждая строка, вписанная напрямую в JSX на Step 4, будет отдельной правкой задним числом. Дешевле завести правило с первого компонента.
