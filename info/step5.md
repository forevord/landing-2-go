# Step 5 — Форма заявки и backend

**Фаза:** Build
**Зависит от:** Step 3 (primitives формы), Step 4 (место в layout, механизм передачи типа услуги)
**Блокирует:** Step 8 (Accessibility формы), Step 9 (QA)

---

## Цель

Полностью рабочая форма заявки — главная точка конверсии сайта (SPEC §2). Клиентская и серверная валидация, защита от спама, понятный успех/ошибка, реальная доставка заявки владельцу бизнеса.

## Контекст из SPEC.md

Раздел 5 (Lead Form Specification) — поля, требования. Раздел 9, требование 4: backend-обработчик как отдельный сервис/endpoint, не встроенная в компонент логика — чтобы позже можно было переключить на CRM без изменения фронтенда.

## Поля формы (обновлено под расширенные УТП)

| Поле | Тип | Обязательное |
|---|---|---|
| Имя | text | Да |
| Телефон | tel | Да |
| Email | email | Нет |
| Тип услуги | select: ворота (распашные / откатные / промышленные / автоматические / калитка / забор) / брукарство / комплексный проект под ключ / не знаю | Да |
| Город | text | Да |
| Комментарий | textarea | Нет |
| Согласие на обработку данных (GDPR) | checkbox | Да, без него submit заблокирован |

## Что делать

1. **UI формы**
   - Собрать из primitives Step 3 (Input, Select, Textarea, Checkbox, Button).
   - Поле «Тип услуги» — предзаполняется, если пользователь пришёл по клику из блока Services (Step 4).
   - GDPR-чекбокс со ссылкой на страницу политики конфиденциальности (заготовка страницы — см. Step 4, Footer).

2. **Клиентская валидация**
   - Мгновенная (on blur / on submit), понятные inline-сообщения под каждым полем — не общий баннер «ошибка формы».
   - Submit заблокирован, пока не отмечен GDPR-чекбокс.

3. **Backend-обработчик (отдельный endpoint)**
   - Next.js API Route (`/app/api/lead/route.ts` или аналог) — не логика внутри клиентского компонента.
   - Серверная валидация полей (дублирует клиентскую — клиентскую можно обойти).
   - Проектировать endpoint так, чтобы получатель заявки (email / webhook / будущая CRM) был конфигурируемым через переменную окружения, а не захардкожен.

4. **Anti-spam**
   - Honeypot-поле (скрытое от пользователя, боты его заполняют — сервер отклоняет заявки с заполненным honeypot).
   - Без визуальной капчи (SPEC §5 — капча снижает конверсию).
   - Rate-limiting на уровне endpoint (простая защита от массовой отправки с одного источника).

5. **Доставка заявки**
   - Определить и настроить фактического получателя: email через транзакционный сервис (Resend/SendGrid/аналог) — простой вариант для MVP.
   - Если получатель на момент разработки не определён окончательно — задокументировать как открытый вопрос и не блокировать разработку тестовым email.

6. **Состояния UI**
   - Loading-состояние кнопки submit (предотвращает двойную отправку).
   - Экран/сообщение успеха: понятный следующий шаг («мы перезвоним в течение X часов»).
   - Понятная обработка ошибки сети/сервера (не просто «что-то пошло не так»).

7. **Мобильная эргономика**
   - Форма помещается в один экран с минимумом скролла на мобильном (SPEC §5).
   - Тип клавиатуры под поля (`inputmode="tel"` для телефона, `type="email"` для почты).

## Критерий готовности

- [ ] Форма отправляется, серверная валидация отклоняет некорректные данные даже при обходе клиентской.
- [ ] Honeypot-поле работает — тестовая отправка с заполненным honeypot отклоняется без ошибки на фронте (бот не должен понимать, что его отклонили).
- [ ] Заявка реально доходит до получателя (проверено тестовой отправкой).
- [ ] Предзаполнение типа услуги из блока Services работает.
- [ ] Экран успеха и обработка ошибок реализованы.
- [ ] Форма проходит визуально на мобильном в один экран без избыточного скролла.

## Почему backend отдельным endpoint

Требование SPEC §9: сегодня получатель — email, завтра может быть CRM-интеграция. Если логика приёма зашита в клиентский компонент, миграция на CRM потребует переписывать фронтенд. Endpoint как граница — фронтенд не знает, что происходит после отправки, кроме успеха/ошибки.
