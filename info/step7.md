# Step 7 — Производительность

**Фаза:** Optimize
**Зависит от:** Step 4 (собранная страница), Step 6 (SEO-разметка не должна ломаться при оптимизации)
**Блокирует:** Step 9 (QA)

---

## Цель

Соответствие Lighthouse-бюджету из SPEC §7 на полностью собранной странице.

## Контекст из SPEC.md

Раздел 7 (Performance & Accessibility), таблица бюджета:

| Метрика | Целевое значение |
|---|---|
| Performance | > 90 |
| SEO | > 95 |
| Best Practices | > 90 |
| Accessibility | > 90 |
| LCP | < 2.5s |
| CLS | < 0.1 |
| INP | < 200ms |

## Что делать

1. **Изображения**
   - Все изображения (Hero, Gallery-плейсхолдеры) — через `next/image` для автоматической генерации WebP/AVIF и `srcset`.
   - Lazy loading для всего, что ниже фолда (Gallery, Testimonials, FAQ и далее) — Hero грузится eager, так как влияет на LCP.
   - Явно заданные размеры (width/height или aspect-ratio) — предотвращает layout shift (CLS).

2. **Шрифты**
   - Уже подключены через `next/font` в Step 3 — на этом шаге проверить, что нет дополнительных внешних шрифтовых запросов (Google Fonts напрямую, например), которые блокируют рендер.

3. **JS-бюджет**
   - Проверить, что тяжёлые библиотеки (если появились где-то в процессе — например, для карты в блоке Contacts) подключены с динамическим импортом (`next/dynamic`), а не в основной бандл.
   - Форма (Step 5) не должна тянуть лишние зависимости в клиентский бандл — валидация может быть на простых нативных проверках, без тяжёлых form-библиотек, если это не оправдано.

4. **Критический путь рендера**
   - Проверить отсутствие render-blocking ресурсов (Lighthouse укажет явно).
   - CSS — Tailwind уже генерирует только используемые классы (JIT), лишний CSS не должен попадать в бандл.

5. **Измерение**
   - Прогнать Lighthouse на задеплоенной (не локальной dev-) версии — dev-сборка Next.js не отражает реальную производительность.
   - Прогнать отдельно на мобильном профиле (Lighthouse mobile throttling) — SPEC требует mobile-first, а не только desktop-показатели.
   - Прогнать на `/pl/` и `/en/` — обе локали должны укладываться в бюджет.

## Критерий готовности

- [ ] Lighthouse Performance > 90, SEO > 95, Best Practices > 90, Accessibility > 90 — на mobile-профиле, на задеплоенной версии.
- [ ] LCP < 2.5s, CLS < 0.1, INP < 200ms.
- [ ] Все изображения через `next/image`, ни одного `<img>` напрямую.
- [ ] Нет render-blocking ресурсов в отчёте Lighthouse.
- [ ] Показатели проверены на `/pl/` и `/en/` отдельно.

## Что делать, если бюджет не проходит

Не переходить к Step 8, пока показатели не в целевом диапазоне — узкие места здесь (тяжёлые изображения, layout shift) обычно проще исправить сразу, чем после того, как поверх наслоятся accessibility-правки.
